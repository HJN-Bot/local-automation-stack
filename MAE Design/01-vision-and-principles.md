# 01 · 愿景与核心原则

> 这是 MAE 项目的"北极星"——每次写代码、做决策前先回看这份

---

## 一、核心愿景：显影

MAE 要解决的根本问题是：**Agent 之间的协作目前对人类是不可见的**。

像照片在显影液里浮现图像一样，让隐藏在后台的 agent 通信过程在飞书群里**可观察、可干预、可复现**。

这不仅是"加日志"，而是把 A2A 通信当作**第一类公民**来设计——每个 agent 都有独立身份（独立 bot 头像和名字），每一步行为都有明确的外部表达。

---

## 二、跨域启发：蚁群群体智能

整个 MAE 的底层类比是**蚁群**。蚁群的协调不靠中央指挥，而靠**信息素**这种"环境中的可见痕迹"。

| 蚁群概念 | MAE 映射 | 设计含义 |
|---------|---------|---------|
| 蚁后（任务发起源） | Airtable | 不直接指挥，只产生任务信号 |
| 信息素通道 | 飞书群聊 | 可见痕迹，所有 agent 共同感知 |
| 基因规则 | Skills + Harness | 定义 agent 如何响应信号 |
| 工蚁分工 | Do/Research/Writer/QA/PM | 角色可弹性切换 |
| 正反馈回路 | 记忆系统（未来） | 高效路径被强化 |
| 阈值响应 | 路由逻辑 | 防止所有 agent 抢同一任务 |

**关键启发**：协调不需要中心化指挥，只需要**可见的痕迹**和**响应规则**。这直接决定了 MAE 的架构选型。

---

## 三、五条不可违背的核心原则

### 1. 显影由 Orchestrator 强制，不靠 Agent 自觉
每个 executor（不管是 Claude API / DeepSeek / Claude Code CLI）都不自己决定是否汇报飞书。Orchestrator 在调用前后强制推送显影消息。

**反面教训**：如果依赖 agent 在 prompt 里"记得汇报"，它会忘。Hook 机制也不可靠。只有**编译期保证**（代码结构强制）才靠谱。

### 2. 描述性 ≠ 可执行
SKILL.md、session-protocol.md 是**行为指南**，不是**运行时**。再详细的指南，没有引擎加载它也不会跑起来。

**辨别方法**：问自己"这个文件不加载进任何 Python 代码，它还有用吗？"如果答案是"它本来就不是给代码用的，是给人看的设计文档"——那没问题。如果期望它能自动驱动行为——那就错了。

### 3. Claude Code 是 Executor 之一，不是执行引擎
曾经设想"用 Claude Code 做整个 runtime"。后来否决：Claude Code 内部 loop 是黑盒，且锁死 Claude 生态。正确定位：**它是众多可调用工具之一**，和 DeepSeek API、Codex CLI 平级。

### 4. Skills 在上、Harness 在中、Tools 在下（Garry Tan 三层）
- **Skills 层**：Markdown，封装判断流程，90% 的价值
- **Harness 层**：~200 行 Python，只做循环/读写/路由/安全
- **Tools 层**：Deterministic，可靠执行（DB、API、搜索）

智能往上推，执行往下推。下次模型升级时，Skills 自动变聪明，Tools 保持可靠。

### 5. Latent vs Deterministic 要分清
每一步只能是两者之一，混了就出 hallucination。

| 适合 Latent（让模型判断） | 适合 Deterministic（代码执行） |
|----------------------|-------------------------|
| 读三份材料综合判断 | SQL 查询 / API 调用 |
| 分类、意图理解 | 数据格式转换 |
| 生成、改写、润色 | 文件读写 |
| 复杂推理 | 条件分支 |

**最常见错误**：把该确定的事扔给模型（浪费 token + 出错），或把该模糊的事写成硬规则（僵硬）。

## 四、四个架构约束

### 约束 1：飞书群 = 显影层（每个 Agent 独立 Bot）
共用 bot + 多人格看起来省事，但所有消息同头像同名字无法分辨——违背显影目标。每个 executor 绑定独立飞书 bot，独立头像、独立名字。

### 约束 2：Airtable 保留，不被飞书替代
Airtable 是任务数据库和派发骨干，飞书是通信/显影层。两者**互补而非冗余**。

流程：Airtable 收到任务 → webhook → Orchestrator → 执行 → 飞书显影 → 状态回写 Airtable。

### 约束 3：Orchestrator 用 Python 自建（~200 行）
否决了 Hermes、LangGraph、CrewAI 作为起点。理由：
- MVP 阶段不需要框架复杂度
- 自建后反而能"反向理解"框架设计
- 未来要迁移 LangGraph 时，概念能自然对应

### 约束 4：诉求优先级顺序（锁定，不讨价还价）
1. **灵活换模型/CLI**（P0）
2. **显影流程统一**（P1）
3. **快速起跑**（P2）

任何新方案都必须通过这个优先级排序的检验。

---

## 五、当前瓶颈：执行层闭环

项目目前所有东西都在"想得很清楚"的状态——架构清楚、记忆设计清楚、显影理念清楚——但**没有一个能自动跑 read→execute→write→report 的引擎**。

最小可行闭环的定义（验收标准 6 条）：
1. Airtable 新建一条任务
2. Orchestrator 自动取到
3. 飞书群出现任务主消息
4. 对应 executor 的 bot 逐步汇报
5. 任务完成，Airtable 状态更新
6. **全程无人工介入**

达成这 6 条，就正式跨过当前瓶颈。Mac Mini 到手后 7 天内完成。

## 六、长期演进方向（不急于做）

- **记忆巩固**：Dreaming 机制，定期把 session 摘要提炼成长期记忆
- **Skill 自生成**：从成功的协作中自动提取 skill 模板
- **信息素可视化**：飞书里高频协作的 thread 显示热度
- **多 agent 并行**：真正的 DAG 式工作流，而非 delegation
- **迁移 LangGraph**：当自建 orchestrator 复杂度超过 500 行时考虑
