# 09 · Postmortem · MAE 之前为什么跑不通

> 这份文档是项目的**核心思维资产**。
> 记录从"加配置"走到"建架构"的认知转变。
> 未来遇到 agent 跑不起来的问题，先回看这份。

---

## 起点：一个真实的问题

2026 年 4 月，Jianan 的真实状态：

> "看一下我现在 auto Claw 相关的技能，我加了很多 harness 相关的东西进去，也加了很多自动化操作的东西进来。但为啥现在 OpenClaw 返回的执行力还是很差，不能真的像是 agent 智能体一样工作？"

> "感觉加的工作流、工作状态、记忆、通信都不能真的让单次对话执行跑起来。"

> "中间的思考也有点笨。"

这些观察非常准。但**根因不在模型，不在配置，不在 skill 数量，而在架构。**

---

## 一、5 个根因（从致命到次要）

### 根因 1：没有 Runtime · 致命

**症状**：触发不了，必须人工每步推。

**本质**：之前所有的尝试——OpenClaw + SKILL.md + harness 配置 + session protocol——都是**描述性的**而非**可执行的**。

打个比方：你写了一本《如何开餐厅》的手册，包括动线、SOP、菜单、品控标准。但**没有厨师、没有炉灶、没有食材供应链**。手册写得再好，菜也出不来。

**触发不了的本质**：claude.ai 的对话模式是"人说一句 → Claude 回一句 → 人再说一句"。它没有"自主循环"的能力——读文件、做决策、写文件、检查结果、继续做下一步——这一切需要外部有个 Python 进程在 while 循环里推动。

**换模型能解决吗？不能。** Claude Opus 5 出来也跑不起来——因为它根本就没被任何东西"启动"。

---

### 根因 2：Skill 是给人看的，不是给代码用的 · 致命

**症状**：加再多 SKILL.md 都没让 agent 变得更自主。

**本质**：你写的所有 SKILL.md、session-protocol.md、harness 红线——它们是**人类阅读时能引导自己（或 Claude 在被提示时）按某种方式工作**的文档。

但它们：
- 不能被 Python 加载并执行
- 没有清晰的 input/output schema
- 没有明确的"何时被触发"
- 没有"完成的判定标准"

这就是为什么"加再多 skill 都不能让单次对话跑起来"——skill 只是引导 Claude 在那次对话里多做几步，但**对话结束 = 一切归零**。

**补配置能解决吗？不能。** 配置已经被加到极致（session 生命周期、三层扫描、changelog、eval 体系都有），结果是配置越来越完美，执行越来越虚。

---

### 根因 3："思考笨"的真正原因 = Latent/Deterministic 错配 · 严重

**症状**："中间的思考也有点笨"——感觉模型不够聪明。

**本质**：原因不是模型不够聪明，而是**让模型做了不该模型做的事，让确定逻辑做了不该确定的事**。

**典型错配场景**：

| 该做什么 | 之前怎么做的 | 结果 |
|---------|------------|-----|
| 查 Airtable 的某条记录 | 让 Claude 读自然语言描述去"理解"任务 | 慢 + 经常理解错 |
| 判断这个任务是研究还是代码 | 写硬规则关键词匹配 | 关键词没覆盖到就分类错 |
| 把 markdown 写到 outputs/ | 描述性指令"请写到 outputs 目录" | 有时写对，有时写到别处 |
| 综合三份资料判断真实意图 | 写 if-else 试图穷举 | 永远穷举不完 |

**正确做法**（Garry Tan "latent vs deterministic"）：
- **该确定的事用代码**（API 调用、文件读写、状态更新）
- **该判断的事用模型**（理解、综合、生成）

混了，就出现"思考笨"——因为模型在被迫做它不擅长的机械操作，或者代码在被迫做它做不到的模糊判断。

**换更聪明的模型能解决吗？不能。** 让 Claude Opus 5 去做"读 Airtable"这种本该是 SQL 的事，它一样会偶尔搞错。

---

### 根因 4：长任务必断 · 严重

**症状**："长时间他可能就不回消息了"。

**本质**：这不是 bug，是物理限制。

- Claude 的 context window 有上限（200k tokens 也是上限）
- 每一步对话都把之前所有内容塞进去
- 任务跑 30 步以上，前面的内容就开始溢出
- 一旦超限，要么报错，要么"忘记"前面，要么直接断掉

**换更大 context 的模型能解决吗？只能拖延，不能根治。** 真正的解法是**架构上隔离 context**——用 subagent 跑子任务，只把摘要传回主线。这不是模型问题，是设计模式问题。

---

### 根因 5：A2A 通信不可见 = 不能调试 · 累积成大问题

**症状**：出 bug 不知道在哪一步出，想优化不知道哪步慢。

**本质**：之前的 OpenClaw 多 agent 架构里，agent 之间的"对话"全在后台。你看到的只是"任务进入"和"任务完成"两个端点，中间发生了什么是黑盒。

这导致：
- 出 bug 不知道在哪一步出
- 想优化不知道哪步慢
- 协作失败不知道哪个 agent 没按预期工作
- 调试只能"重跑看看"——但重跑结果还可能不一样

**这不是模型问题，是观测性问题。** 你需要的是**强制每一步都对外暴露**，不是更聪明的模型。

## 二、换模型 / 补配置能不能跑通？

**直接给答案：都不行。**

| 方案 | 解决根因 1 | 解决根因 2 | 解决根因 3 | 解决根因 4 | 解决根因 5 |
|-----|---------|---------|---------|---------|---------|
| 换 Claude Opus 5 | ❌ 还是没 runtime | ❌ skill 还是文档 | ⚠️ 缓解但不根治 | ⚠️ 拖延 | ❌ 黑盒还是黑盒 |
| 加更多 SKILL.md | ❌ 加再多也不会跑 | ❌ 加深问题 | ❌ 越加越乱 | ❌ 无效 | ❌ 无效 |
| 加 cron 提醒 | ⚠️ 有触发但跑不下去 | ❌ 没用 | ❌ 没用 | ❌ 没用 | ❌ 没用 |
| 加记忆系统 | ❌ 没东西可记 | ❌ 没用 | ❌ 没用 | ⚠️ 部分缓解 | ❌ 没用 |
| 换 OpenRouter 多模型 | ❌ 同上 | ❌ 同上 | ⚠️ 略有改善 | ❌ 同上 | ❌ 同上 |

**有效的方案 = 必须从架构层补 5 个先天缺陷**：

| 根因 | 唯一的根治方案 |
|-----|------------|
| 没 Runtime | 写一个 Python 进程做 while 循环（Orchestrator） |
| Skill 不可执行 | 区分"给人看的文档" vs "给代码用的 skill 文件"（带 frontmatter，能被加载） |
| Latent/Deterministic 错配 | 严格分层：Skills（latent）/ Harness（流程）/ Tools（deterministic） |
| Context 必爆 | Subagent 隔离 + 状态 checkpoint + 摘要传递 |
| 不可见 | Orchestrator 强制每步推飞书（不靠 agent 自觉） |

**这 5 个根治方案，本质上就是新方案的全部内容**。这不是巧合——新架构就是为了堵这 5 个洞设计的。

## 四、还有 3 个之前没充分讨论的次级问题

复盘完根因，还有 3 个之前**没专门讨论但其实也存在**的问题。这些不是致命的，但 Mac Mini 跑起来后会陆续暴露出来。**这 3 项已经分别有专门文档**：

### 次级 1：错误处理与重试

之前的 OpenClaw 出错时基本就是"卡住"或"无响应"。新方案需要：
- 区分可重试 vs 不可重试错误
- 死信队列（多次失败的任务隔离出来）
- 错误模式学习

详见 **`10-error-handling-and-retry.md`**。

### 次级 2：成本控制 / 资源 Guard

之前用单一模型 = 简单任务也用贵模型。新方案虽然 Router 已经分层（DeepSeek/Claude/Claude Code），但**没有预算 guard**。

需要补：
- 单任务成本上限
- 每日总预算
- 每个 executor 的 token 用量统计 + 飞书显影

详见 **`11-resource-guards.md`**。

### 次级 3：并发控制

新方案目前是**串行执行**。任务多了会很慢。

未来补充方向：
- 简单情况：`asyncio` + `aiohttp` 并发
- 复杂情况：迁移到 LangGraph 用真正的 DAG

这一项不紧急，列入 `07-todos` 的 P3。

## 五、一句话总结复盘

之前跑不通是因为你**在做"AI 协作工作流"，而不是在做"AI 自主系统"**——前者需要人在每一步推动，后者需要代码在每一步推动。

换模型、加配置都是在优化"人推动"的体验，但**核心问题是缺少代码在推动**。

新方案的本质就是**把那个推动者从你（人）替换成 Orchestrator（代码）**。一旦这个替换完成，模型够用就行（DeepSeek + Claude Sonnet 完全够），配置不用太复杂（200 行 Python 就能起步）。

## 六、未来诊断框架

未来看到任何"agent 跑不起来"的问题，按这个顺序问自己：

```
1. 这个 agent 有 runtime 在持续推它吗？
   有 → 进入 2
   没 → 加 runtime（Python while 循环 / cron / 框架）

2. 这个 agent 的"指令"是代码能加载的格式吗？
   是 → 进入 3
   否 → 把 SOP 转成可加载的 skill 文件

3. 这一步是该模型判断还是该代码执行？
   分清 → 进入 4
   混淆 → 拆开成两步

4. 这一步执行时对外可见吗？
   是 → 进入 5
   否 → 加显影（log / 飞书 / LangSmith）

5. 这一步会爆 context 吗？
   不会 → 完成
   会 → 用 subagent 隔离
```

跑通这 5 关，agent 就不会"跑不起来"了。换模型只是 step 3 的微优化，不是关键。

## 七、最大的认知收获

**项目最有价值的不是"建好了一个 agent 系统"，而是"想清楚了什么是 agent 系统"**。

具体说：

1. **架构 > 模型**：再聪明的模型，没有正确的架构包裹，跑不出价值
2. **可执行 > 描述性**：能被代码加载的指令，永远打败"写得很好的文档"
3. **强制 > 自觉**：让 agent 自觉显影 = 它不会显影；让 orchestrator 强制显影 = 必然显影
4. **隔离 > 共享**：subagent 独立 context = 长任务能跑；共享 context = 必爆
5. **观测 > 优化**：看不见就改不了，加 log 永远是优化的第一步

这 5 条不仅适用于 MAE，适用于所有 agent 系统设计。

## 八、一个有趣的思考

为什么会陷入"加配置"的陷阱？因为：

- 写文档**有即时反馈**（看着文件越来越完善）
- 写代码**反馈慢**（要跑通才知道行不行）
- 文档**改来改去成本低**
- 代码**改了要测**

所以容易掉进"在文档上精益求精"的舒适区。

**破解方法**：定期问自己——"这一周我加了多少行**会被代码加载执行**的内容？"如果答案是 0，那就是在写文档自嗨，不是在建系统。
